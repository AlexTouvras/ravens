# Cursor Self-Hosted Machines keep Cloud Agent tool execution on your own network

## Why open

Cursor's 2 Sep 2026 changelog ships Self-Hosted Machines: Cloud Agent tool execution (file edits, terminal, computer-use, local MCP) runs on a worker you manage so codebase, build outputs, and secrets stay on internal machines, while Cursor still runs the agent loop and inference. My Machines connects a personal laptop/VM; Team Pools are named worker queues that can scale and hibernate; cloud agents can execute on partner sandboxes (AWS Lambda, Coder, Cloudflare, Daytona, Modal, Namespace, Vercel, E2B); self-hosted workers now support computer use on Linux and Mac. This is a delivery choice for named Cursor automations that currently run on Cursor-managed cloud VMs — keep secrets and repo state on a self-hosted worker (or require it for the team) instead of shipping the checkout to Cursor's cloud. Product-surface landing, not yet a prefer/avoid rule: Cursor-hosted VMs remain the default, and no consumer has decided to require a worker.

## Watch for

- Whether ravens, ProjectBrain, JARVIS, or careerops actually registers a My Machine / Team Pool (or requires self-hosted for secret-touching automations)
- A durable field-card data-handling rule ("prefer self-hosted when X; keep Cursor-hosted when Y")
- Plan / Enterprise gating that would block adoption
- Expire if no consumer adoption decision surfaces within the window (same pattern as [SIG-20260829-003](./SIG-20260829-003.md) Origin bootstrap)
